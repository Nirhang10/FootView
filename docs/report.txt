1. INTRODUCTION
================================================================================

The Football Score Information System is a desktop application developed using
JavaFX and MySQL, designed to provide an efficient platform for managing and
viewing football-related information including teams, players, matches, and
league standings.

The system serves two types of users:
  - Customers: Fans who want to view team statistics, match results, and
    league standings.
  - Admins: Staff who manage all data in the system including CRUD operations
    on teams, players, matches, and user accounts.

The application uses a client-server architecture where JavaFX provides the
graphical user interface and MySQL serves as the persistent data store.

8. ACTIVITY DIAGRAM DESCRIPTION
================================================================================

Login Activity:
  1. User enters username and password
  2. System validates fields are not empty
  3. System queries database for user by username
  4. If user not found → show error "Invalid credentials"
  5. If user found → verify BCrypt password hash
  6. If password incorrect → show error "Invalid credentials"
  7. If user status is BLOCKED → show error "Account blocked"
  8. If all checks pass → update last_login timestamp
  9. Redirect to Customer Dashboard or Admin Dashboard based on user_type

Match Score Update Activity (Admin):
  1. Admin selects a match from the matches table
  2. Admin clicks "Update Score"
  3. Dialog appears with current scores and status
  4. Admin enters new scores and selects status (e.g., COMPLETED)
  5. System calls updateScore() in MatchDAO
  6. MySQL trigger fires: updates team wins/draws/losses/goals/points
  7. Success message displayed; table refreshes

10. DATABASE DESIGN (ERD)
================================================================================

The system uses four main tables with the following relationships:

  users (1) ───────────────────────── (user registers/logs in)

  teams (1) ──────────────── (M) players    [one team has many players]
  teams (1) ──────────────── (M) matches    [as home_team_id]
  teams (1) ──────────────── (M) matches    [as away_team_id]

ERD Entities:
  [users] ──── user_id (PK), username (UQ), email (UQ), password_hash,
               user_type, status, created_at, last_login

  [teams] ──── team_id (PK), team_name (UQ), founded_year, stadium, coach,
               city, logo_url, wins, draws, losses, goals_for, goals_against,
               points, created_at, updated_at

  [players] ── player_id (PK), team_id (FK→teams), player_name, position,
               jersey_number, date_of_birth, nationality, height, weight,
               matches_played, goals, assists, yellow_cards, red_cards, created_at

  [matches] ── match_id (PK), home_team_id (FK→teams), away_team_id (FK→teams),
               match_date, match_time, home_score, away_score, status,
               created_at, updated_at

12. DATA DICTIONARY
================================================================================

users table:
  user_id       - Unique identifier for each user (auto-generated)
  username      - Unique login name chosen by the user
  email         - User's email address (must be unique and valid format)
  password_hash - BCrypt-hashed version of the user's password
  user_type     - Either CUSTOMER (regular user) or ADMIN (administrator)
  status        - ACTIVE (can login) or BLOCKED (cannot login)
  created_at    - Timestamp when the account was created
  last_login    - Timestamp of the most recent successful login

teams table:
  team_id       - Unique identifier for each team
  team_name     - Official name of the football team
  founded_year  - Year the team was founded
  stadium       - Name of the team's home stadium
  coach         - Name of the head coach/manager
  city          - City where the team is based
  logo_url      - URL or path to the team's logo image
  wins          - Total number of wins in the current season
  draws         - Total number of draws in the current season
  losses        - Total number of losses in the current season
  goals_for     - Total goals scored by the team
  goals_against - Total goals conceded by the team
  points        - Total league points (3 per win, 1 per draw)
  created_at    - Record creation timestamp
  updated_at    - Record last update timestamp

players table:
  player_id     - Unique identifier for each player
  team_id       - Foreign key linking player to their team
  player_name   - Full name of the player
  position      - Playing position (Goalkeeper/Defender/Midfielder/Forward)
  jersey_number - Squad number worn on the player's shirt
  date_of_birth - Player's date of birth
  nationality   - Player's country of origin
  height        - Player's height in centimetres
  weight        - Player's weight in kilograms
  matches_played- Number of matches the player has played
  goals         - Total goals scored by the player
  assists       - Total assists provided by the player
  yellow_cards  - Number of yellow cards received
  red_cards     - Number of red cards received
  created_at    - Record creation timestamp

matches table:
  match_id      - Unique identifier for each match
  home_team_id  - Foreign key for the home team
  away_team_id  - Foreign key for the away team
  match_date    - Date when the match is/was played
  match_time    - Kick-off time for the match
  home_score    - Goals scored by the home team
  away_score    - Goals scored by the away team
  status        - Current state of the match (SCHEDULED/IN_PROGRESS/
                  COMPLETED/POSTPONED/CANCELLED)
  created_at    - Record creation timestamp
  updated_at    - Record last update timestamp

13. IMPLEMENTATION
================================================================================

Object-Oriented Programming Concepts Applied:

1. Encapsulation
   - All model classes (User, Team, Player, Match) have private fields with
     public getters and setters, protecting internal data.

2. Inheritance
   - Controllers use JavaFX base classes (inheriting FXML functionality).

3. Polymorphism
   - Enum types (User.UserType, Player.Position, Match.Status) provide
     type-safe polymorphic values used throughout the system.

4. Abstraction
   - DAO classes abstract all database operations from the controllers.
   - Utility classes abstract common operations (hashing, validation, alerts).

Design Patterns Used:

1. Singleton Pattern (DatabaseConnection)
   - Ensures only one database connection instance exists at runtime.

2. Data Access Object (DAO) Pattern
   - Separates database logic from business logic and UI.
   - Each entity (User, Team, Player, Match) has its own DAO class.

3. MVC Pattern (Model-View-Controller)
   - Models: com.football.models package
   - Views: FXML files in src/main/resources/fxml/
   - Controllers: com.football.controllers package

Key Implementation Details:
  - BCrypt password hashing with work factor 10 for secure credential storage
  - PreparedStatement usage to prevent SQL injection attacks
  - JavaFX PropertyValueFactory for binding model fields to TableView columns
  - JavaFX Dialog API for in-application CRUD forms
  - FXML for clean separation of UI layout from Java code

14. COMPUTATIONAL THINKING APPROACH
================================================================================

Decomposition:
  The problem was broken into smaller sub-problems:
  - User authentication system
  - Team management module
  - Match management module
  - Player management module
  - Statistics/standings calculation

Pattern Recognition:
  - All CRUD operations follow the same pattern: load → display → action → refresh
  - All DAO classes follow the same structure: connection, CRUD methods, mapper
  - All dialogs follow the same pattern: Dialog → GridPane → ResultConverter

Abstraction:
  - DatabaseConnection hides connection complexity
  - PasswordUtil hides BCrypt complexity
  - AlertUtil hides JavaFX Alert complexity
  - ValidationUtil hides regex and validation logic

Algorithmic Thinking:
  - Login authentication: query → verify hash → check status → redirect
  - League standings: ORDER BY points DESC, goal_difference DESC
  - Team stats update: triggered automatically on match completion

17. DISCUSSION AND REFLECTION
================================================================================

The Football Score Information System successfully meets all the specified
requirements. The application demonstrates a solid understanding of:

1. Object-Oriented Programming: Clean separation of models, DAOs, controllers,
   and utilities makes the codebase maintainable and extensible.

2. Database Design: The relational schema with foreign keys ensures referential
   integrity. The use of triggers for automatic stat calculation demonstrates
   advanced database knowledge.

3. Security: BCrypt password hashing ensures that even if the database were
   compromised, user passwords would not be directly exposed. Prepared statements
   prevent SQL injection.

Challenges Encountered:
  - Coordinating the JavaFX MVC pattern with FXML required understanding the
    lifecycle of FXML controllers and the initialize() method.
  - The Database trigger for auto-updating team stats required careful logic
    to handle wins, losses, and draws correctly.

Future Improvements:
  - Add search/filter functionality to tables
  - Implement a match commentary/events log
  - Add player photo upload functionality
  - Create match statistics breakdown (shots, possession, etc.)
  - Add export functionality for reports (PDF/Excel)
  - Implement real-time score updates using background threads
